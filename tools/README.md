# Tools

- **devtools/**: Browser extension (Chrome/Firefox) for debugging Owl components. Provides a devtools panel to inspect component tree, state, and lifecycle.
- **playground/build_monaco.mjs**: Bundles the Monaco editor and its workers for the playground.
- **compile_owl_templates.mjs**: CLI tool that compiles Owl XML templates into JavaScript. Reads template files from provided paths and writes compiled output to a file.
- **playground/server.py**: Python HTTP server that serves the playground locally, resolving Owl builds and disabling caching. Run with `npm run playground:serve`.
- **odoo_migration/**: Odoo template migration and compilation checks, including template inheritance comparisons between Owl builds. The checkers exit 2 on a root that does not exist or holds no template, and on a `packages/owl/dist` built from other sources than those beside it. `compare_codegen.mjs <roots>` compiles every static template (`static/src/**/*.xml`) and every inline `xml` `` template (`static/{src,tests}/\*_/_.js`) of the roots with two compilers, `--old`(default: the one vendored in Odoo's`web`) and `--new`(default: this checkout's`packages/owl/dist`), and exits 1 on any template whose code differs or that only the new one rejects; `npm run verify` runs it over the Odoo checkout and its sibling module repos.
- **odoo_gate.mjs**: Runs Odoo's HOOT suites on two OWL builds and reports the differences test by test (`--old`, default `vendored`: Odoo's `web/static/lib/owl`; `--new`, default `worktree`: this checkout as it is; or any git revision). Each build gets a detached worktree of the Odoo checkout (its crate sources copied, so the shared native extension stays fresh), each addon of `--suites` (default `/web:WebSuite,/web:MobileWebSuite,/mail:MailSuite,/mail:MobileMailSuite`) a scratch database per side; both sides run at once, and each checks that its server serves its build. It exits 1 on a HOOT test or a Python-side test that fails only on the new build, and drops its databases and worktrees unless `--keep`. `--bisect <suite tag> --test <HOOT test name> --good <rev> --bad <rev>` finds the first OWL commit that makes that one test fail, after checking both ends.
- **hooks/pre-push**: With `git config core.hooksPath tools/hooks`, every push runs `npm run verify` on each commit the pushed refs carry, once (an annotated tag counts as the commit it names), in a throwaway worktree (uncommitted changes neither help nor hurt), and is refused when it fails; `git push --no-verify` skips it. The connection git opened before the hook idles meanwhile: on a loaded machine push with `GIT_SSH_COMMAND='ssh -o ServerAliveInterval=30'`, or the remote closes it.
- **vendor_odoo.mjs**: Builds this checkout and vendors it into Odoo: `npm run vendor:odoo -- --check` compares the build with `web/static/lib/owl/` and the `owl` entry of `web/static/lib/versions.json` and exits 1 on a difference; without `--check` it copies the three files and updates that entry (commit, checksums, version). A commit no remote branch contains (as of the last fetch) is refused, so Odoo never pins a commit no other clone can fetch; `--allow-unpushed` overrides it, and `--check` reports a pinned commit no remote branch contains. `--check` also applies Odoo's `check_vendored_libs.py` rules: the checksums pin exactly the three files, the entry's `probe` matches, each file's `var buildHash` is the pinned commit's. The version written is the build's own (`owl-runtime/src/version.ts`); a `packages/owl/package.json` that disagrees is refused. `--odoo <path>` names the Odoo checkout (default: `../odoo` beside this one, nothing else). Refused: any uncommitted change to a tracked file anywhere in the checkout (`git status --porcelain --untracked-files=no` not empty) and any untracked file under `packages/*/src`; untracked files elsewhere (e.g. `__pycache__`) are allowed.
- **mutation/**: Mutation testing of the core's four hot spots (`computations.ts`, `proxy.ts`, `fibers.ts`, `scheduler.ts`; `targets.mjs`). `npm run mutate` runs Stryker's standard mutators (vitest runner, per-test coverage, a sandbox under `temp/stryker-tmp`) and OWL's own operators (`operators.mjs`), which Stryker has no plugin API for: `path` drops one inner segment of a member chain, through a `const` alias too (`root.node.app.scheduler` with `const root = this.root!` gives `this.node.app.scheduler`, the defect of `ef4e3258`); `receiver` replaces a chain's head with another local of the function read with the same property elsewhere; `swap` exchanges two adjacent statements of a block. The operators skip debug output (`debugLog`, `if (debug.<channel>)`), left to Stryker, and swaps with a literal declaration the other statement does not name. Each custom mutant runs in one of several sandboxes (`temp/mutation-sandboxes`) against only the test files whose v8 coverage reaches it (cached per test file in `temp/mutation/<package>/coverage-map.json`), bailing on the first failure, after the unmutated sandbox passed them. `--mutate <file>` (repeatable) narrows the files, `--stryker` or `--custom` the tools, `--operator` and `--line` the custom mutants, `--incremental` reuses Stryker's previous results; `--concurrency <n>` sets the workers. Reports: `temp/mutation/<package>/index.html` and `report.json` (Stryker), `custom.json`, and `temp/mutation/summary.json`. A survivor that no test can kill is listed with its reason in `mutation/equivalent.json`, matched by tool, file, line, operator, original and replacement; it exits 1 on any other survivor and names equivalent entries that no longer match.
- **benchmark_reactivity.mjs**: Debug-validates tracked reads, selective notifications, collection mutations and proxy/observe iterators, then measures them with logging disabled. Run with Node 26 (refused below) using `npm run bench:reactivity -- --baseline /path/to/baseline/owl --output temp/reactivity.json`. The baseline is optional. Rounds alternate module order; source hashes and checksums are checked again after timing. Each reported iteration performs one read or write, two mutations for insert/delete, or consumes 32 iterator values. Tracked-read loops include effect creation/disposal, amortized over the loop. The Vitest core benchmarks also expose these workloads, with 128 iterations per sample. Treat its cross-workload rankings as workload cost comparisons.
- **benchmark_browser.mjs**: Uses local Chrome to compare selection, 20-row updates, and navigation to a detail view and back in a 200-row app: `npm run bench:browser -- --baseline /path/to/baseline/owl --output temp/navigation.json`. Checks committed DOM, selective render counts and subscription cleanup before and during timing. It builds each checkout independently, adding diagnostic exports from the same core instance, and removes its browser profile and HTTP listener afterward. Commit latency includes animation-frame waits; instrumented render-function time covers only part of the pipeline. This synthetic app does not measure Odoo application performance. Run timing comparisons serially and repeat with baseline/candidate roots reversed to check order effects.
